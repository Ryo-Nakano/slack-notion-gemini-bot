# Slack Bot（Gemini + Notion MCP）回答精度向上ガイド

> 対象構成: Slack → Slack Bot（Cloud Run）→ Gemini API（自前ブリッジ）→ Notion MCP Server → Notion

---

## 1. 回答精度を左右する要素（優先度順）

| 優先度 | 要素 | 概要 |
|:---:|---|---|
| ★★★ | ツール定義（Functionのdescription） | LLMがいつ・どのツールを使うかの判断根拠 |
| ★★★ | システムプロンプトのNotionデータ構造記述 | どのDBにどんなプロパティがあるかを教える |
| ★★☆ | 質問タイプ別の検索戦略 | 質問パターンに応じた推奨アクションの明示 |
| ★★☆ | ReActパターンの指示 | 計画してからツールを使う思考フローの促進 |
| ★☆☆ | Few-shotサンプル | 良い回答例をプロンプトに含める |

---

## 2. ツール定義の作り込み

LLMは「ツール定義のdescription」を根拠に、どのツールをいつ使うかを判断する。
ここが曖昧だと、システムプロンプトをどれだけ整備しても意図通りに動かない。

### NG例（曖昧）
```json
{
  "name": "search_notion",
  "description": "Notionを検索する"
}
```

### OK例（具体的）
```json
{
  "name": "query_notion_database",
  "description": "構造化されたNotionデータベースをプロパティ条件で検索する。日付・タグ・担当者など明確な条件で絞り込む場合に使う。例: 昨日の議事録、〇〇さんの担当タスク、先週の意思決定",
  "parameters": { "..." : "..." }
}
```

### ツール別のdescription設計方針

| ツール | descriptionに含めるべき内容 |
|---|---|
| `query_database` | 構造化DBへの条件検索であること。プロパティ（日付・タグ等）で絞れる場合に使う旨 |
| `search` | キーワード全文検索であること。DBをまたいで広く探す場合に使う旨 |
| `retrieve_page` | 特定ページの本文取得であること。page_idが判明している場合に使う旨 |

## 3. システムプロンプトの設計

### 3-1. Notionのデータ構造を記述する

LLMがどうクエリすべきかを推論できるように、DBのプロパティ構造を教える。

```
## Notionのデータ構造

### 議事録DB
- title: ページタイトル
- date: 開催日（date型）
- participants: 参加者（multi-select型）
- tags: タグ（multi-select型）
- project: 関連プロジェクト（relation型）

### 決定事項DB
- title: 決定内容
- decision_date: 決定日（date型）
- related_project: 関連プロジェクト（relation型）
- owner: 担当者（person型）

### Wikiページ
- 構造化プロパティなし
- フルテキスト検索（search）のみ有効
```

### 3-2. 質問タイプ別の検索戦略を記述する

```
## 質問タイプ別の検索戦略

- 「〇〇の議事録を探して」
  → query_database(議事録DB, date条件) → retrieve_page で本文取得

- 「〇〇の決定事項は？」
  → query_database(決定事項DB, キーワード or 期間条件) → 複数件を要約して回答

- 「〇〇について教えて」
  → search(キーワード) → retrieve_page → 内容を要約して回答

- 検索結果が0件のとき
  → 別のキーワードや期間で再検索。それでも見つからない場合はその旨を正直に伝える
```

### 3-3. ReActパターンの指示

「計画してから動く」思考フローを明示的に促すだけで精度が上がる。

```
## 行動指針

ユーザーの質問に答える前に、以下のステップで考えてください。

1. 質問を分析し、何を探すべきかを特定する
2. どのNotionデータベース・ツールを使うべきか判断する
3. ツールを実行し、結果を確認する
4. 情報が不十分な場合は追加検索を行う
5. 取得した情報をもとに回答を生成する
```

### 3-4. Few-shotサンプル（任意）

良い回答例を数件含めると、期待する挙動に近づけやすい。

```
## 回答例

ユーザー: 先週の開発チームの議事録教えて
思考プロセス:
  - 「先週」の日付範囲を計算する
  - query_database(議事録DB, date: 先週の範囲, participants or tags: 開発チーム)
  - ヒットしたページをretrieve_pageで取得
  - タイトル・日付・主な議題を整理して回答
```

## 4. スキーマ情報のキャッシュ戦略

Notionのプロパティ構造をリクエストの度に取得するのは非効率。
**インメモリキャッシュ（TTL: 1〜数時間）** がシンプルで現実的な対応。

```python
import time

_schema_cache = {"data": None, "fetched_at": 0}
CACHE_TTL = 3600  # 1時間

def get_notion_schema():
    now = time.time()
    if _schema_cache["data"] and now - _schema_cache["fetched_at"] < CACHE_TTL:
        return _schema_cache["data"]

    schema = notion_mcp.retrieve_database(db_id)
    _schema_cache["data"] = schema
    _schema_cache["fetched_at"] = now
    return schema
```

> **注意**: Cloud Runはインスタンスがスケールアウトするとキャッシュが共有されない。
> コールドスタート頻度が問題になるようであれば、Cloud MemorystoreやGCSへの外部キャッシュを検討する。
> ただし本構成の規模では、まずインメモリで様子見するのが現実的。

## 5. 精度改善の進め方

段階的に改善するのが現実的。一度に全部やらない。

```
Step 1: まず動かす
  └─ ツール定義とシステムプロンプトの最小版でとにかく動作確認

Step 2: 精度を計測する
  └─ 想定質問リストを用意し、どの質問タイプで精度が落ちるかを特定

Step 3: ボトルネックに集中して改善する
  └─ 特定ドキュメント検索が弱い → ツール定義を見直す
  └─ 横断検索が弱い → 検索戦略の記述を強化する
  └─ 見当違いの回答が多い → ReAct指示やFew-shotを追加する

Step 4: Notionのデータ整備も視野に入れる
  └─ 議事録の決定事項をDB化するなど、構造化が進むと検索精度が上がる
```

## 6. 限界と注意事項

どれだけプロンプトを整備しても、以下は構造的に難しい。

| 限界 | 理由 | 対策候補 |
|---|---|---|
| 表現の揺れへの対応（「合意した」vs「決めた」） | Notion APIはキーワードマッチのみ | RAG（フェーズ2B）への移行を検討 |
| 大量の議事録の横断検索 | 件数が増えるとAPI呼び出し回数・コストが増大 | ページ取得に上限を設けてLLMに要約させる |
| Notionのデータ品質に依存 | タイトルや日付が不整備だと検索精度が落ちる | Notionの運用ルール整備と並走させる |
